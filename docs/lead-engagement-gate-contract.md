# Lead engagement gate backend contract

This change extends the existing `profile_lead_deliveries` queue and `lead_distribution_cycles` ledger. It does not add a second queue or change the Muse claim/result protocol.

## Scan rules

- Count one completed discovery scan per successful or partial `scan_runs.search_job_id` received after the profile's `policy_activated_at`. Claim retries and duplicate acknowledgements keep the same `search_jobs.id`, so they count once. Failed runs do not advance the stage.
- Scans one and two always distribute from the profile's eligible pending pool, up to ten distinct leads each.
- Scan three is claimed and run normally. Its results are stored and added to the pending ledger. If current engagement is below 80%, that scan's cycle delivers zero; pending candidates are retained and not-yet-claimed pending/authorization-blocked search jobs are canceled with `last_error = 'usage_gate'`. Valid claimed leases continue to completion.
- Later scans are neither materialized by recurring scheduling nor claimed while the gate is closed. Manual requests return `usage_gated`. Once review progress reaches the threshold, the same transaction distributes one pending batch and the next normal scheduled slot can resume.
- A qualifying review event has a unique `(search_profile_id, normalized_url)` key. Its unlock cycle key is `unlock:<normalized URL>`; scan cycles use `scan:<search_job_id>`. Replayed requests cannot create another batch.

## Engagement formula

The denominator is distinct source URLs in `profile_lead_deliveries` with state `delivered` and `delivered_at >= policy_activated_at`. The numerator is distinct URLs in `lead_engagement_reviews` for that delivered cohort. Eligibility uses integer-equivalent arithmetic: `reviewed_count >= ceil(delivered_count * 0.8)`; the reported percentage is not rounded before that comparison. A zero denominator is eligible. New delivery changes the denominator and eligibility is recalculated immediately.

Review evidence is one of:

- An authenticated `POST /api/leads/:id/source-open` generated by the deliberate Facebook source click. The browser already sends it with `keepalive` without delaying navigation. The existing account-wide `lead_source_opens` record remains intact; the new per-profile review row is written in the same server transaction.
- An authenticated manual workflow decision to `contacted`, `interested`, `not_fit`, or `not_interested`. Repeated status changes cannot add more than one review. `new` and `seen` do not count.

Rendering, polling, an old `seen` value, and source opens before the policy baseline do not count.

## API fields for customer integration

`GET /api/profiles/:id/scan` keeps its existing `scan`, `version`, and all-time `leadCount` fields and adds a read-only `engagement` object:

```ts
type LeadEngagementGate = {
  policyActive: boolean;
  completedDiscoveryScans: number;
  deliveredCount: number;
  reviewedCount: number;
  requiredReviewedCount: number;
  reviewedPercent: number;
  thresholdPercent: 80;
  pendingCount: number;
  gateState: 'first_two_scans' | 'eligible' | 'holding_third_scan_results' | 'awaiting_review';
  mayStartNewScan: boolean;
  mayReceivePendingLeads: boolean;
  nextAction: 'none' | 'review_leads' | 'deliver_pending';
};
```

The existing `scan` object remains the search execution state. It is separate from `engagement.gateState`, account-level Admin suspension, and a profile's own enabled/paused value. `POST /api/profiles/:id/scan` may return `{ scan: { outcome: 'usage_gated' } }` without creating a job.

`GET /api/admin/users/:userId` adds these per-profile fields: `allTimeLeadCount`, `policyActive`, `completedDiscoveryScans`, `deliveredCount`, `reviewedCount`, `requiredReviewedCount`, `reviewedPercent`, `pendingCount`, `gateState`, and `searchingPausedByUsagePolicy`. Existing `leadCount` and scan fields remain available.

`GET /api/leads` is read-only with respect to delivery. Only a completed scan result or the unique review event that opens the gate may start a distribution cycle; refreshes cannot expose another batch.

## Rollout and compatibility

Migration `026_lead_engagement_gate.sql` adds a per-profile activation baseline, a minimal private review ledger, and the profile-creation trigger. Existing settings rows receive the migration-time timestamp. Historical deliveries, statuses, and source opens remain unchanged and are excluded because their delivery timestamps precede that baseline. No synthetic review rows are created. New profiles get their baseline at profile creation; edits to names or descriptions do not reset it.

The migration is additive and is not applied to Production by this change. Apply migration 026 before deploying the code. The existing quiet-hours helper remains the scan execution boundary: claims stop during 00:30–06:30 Asia/Ho_Chi_Minh, while an authenticated review may release already-stored leads without calling the search scheduler.

All delivery entry points use the existing account/profile transaction locks. Scan result ingestion, scan progression, pending insertion, bounded delivery, and usage-gate queue cleanup commit together. Manual review, its unique evidence row, eligibility recalculation, and any unlock batch commit together. Cross-profile duplicate-permalink exclusion, pending expiration, candidate ranking, Hot Lead assessment/priority, and push outboxes remain in the existing distribution pipeline.

The admin profile metrics are an API contract only; no Admin or customer UI integration is included here.
